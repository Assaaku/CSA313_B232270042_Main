## SLO / Threshold

5 VU baseline туршилтын p95 latency нь `227.95 ms` байсан.

SLO-г baseline p95 × 1.5 зарчмаар тодорхойлов:

`227.95 × 1.5 = 341.925 ms`

Иймээс latency SLO-г `p(95) < 342 ms` гэж сонгосон.
Baseline-аас 50% хүртэл хэлбэлзэл зөвшөөрөхийн зэрэгцээ
гүйцэтгэл мэдэгдэхүйц муудахыг илрүүлэх зорилгоор энэ утгыг сонгов.

Мөн error rate-ийн SLO-г:

`http_req_failed < 1%`

гэж тохируулсан.

`p(95) < 342 ms` threshold бүхий туршилт PASS болсон.
Threshold-ийг зориудаар `p(95) < 50 ms` болгон хатууруулж,
FAIL гаралтыг мөн шалгасан.

## Дүгнэлт

5 VU ачааллын үед p95 latency 227.95 ms байсан.
30 VU үед p95 latency 228.85 ms болж маш бага өссөн.
100 VU үед p95 latency 231.87 ms болсон бөгөөд ачаалал ихэссэн ч p95 харьцангуй тогтвортой байв.
Throughput 5 VU үед 7.64 req/s байсан бол 30 VU үед 45.53 req/s, 100 VU үед 151.78 req/s болж өссөн.



Бүх гурван туршилтын error rate 0% байсан тул хүсэлтүүд амжилттай боловсруулагдсан.
Гэхдээ maximum response time 299.73 ms-ээс 1.18 s хүртэл өссөн нь өндөр ачааллын үед зарим хүсэлт удааширч болохыг харуулсан.



Энэ туршилтаар ачаалал нэмэгдэхэд throughput өсөх боловч latency-ийн tail утгууд өөрчлөгдөж болохыг ажиглав.
5 VU baseline p95 дээр үндэслэн SLO-г 342 ms гэж тодорхойлсон бөгөөд бодит threshold туршилтаар энэ шаардлага хангагдсан.
Харин p95 < 50 ms гэсэн зориудаар хатуу threshold FAIL болсон нь k6 threshold-ийг CI pipeline-ийн performance quality gate болгон ашиглаж болохыг харууллаа.
