# 1. Туршилтын API

Энэ лабораторид локал Express API ашигласан. API нь өөр өөр чанарын шинжийг шалгах зориулалттай дараах endpoint-үүдтэй.

| Endpoint | Төрөл | Зан төлөв |
|---|---|---|
| `POST /cart/add` | Performance | Маш хурдан хариу өгнө |
| `GET /report` | Performance | Санаатайгаар 200–400 ms delay-тэй |
| `POST /pay` | Reliability | Ойролцоогоор 5% хүсэлтэд HTTP 500 алдаа өгнө |

Өмнөх лабораторид бодит, сүлжээгээр хандах тестийн сервер ашигласан бол энэ удаагийн тест localhost дээр хийгдсэн. Ингэснээр интернетийн latency, packet loss, routing болон гаднын серверийн ачаалал зэрэг хувьсагчдыг бараг бүрэн хасаж, API-ийн өөрийн зан төлөв болон зориудаар үүсгэсэн эвдрэлд төвлөрөх боломжтой болсон. Production орчин яг ийм цэвэр байхгүй боловч локал орчин дээр ч performance, reliability болон availability failure-уудыг бодитоор үүсгэж хэмжих боломжтой байгаа нь сонирхолтой санагдсан.

# 2. Чанарын сценарионууд

### Performance — `/cart/add`

Систем хэвийн ажиллаж байх үед 20 VU `/cart/add` руу хүсэлт явуулна. Сервер HTTP 200 хариу өгөх ёстой. Гол хэмжүүр нь p95 latency бөгөөд **20 ms-ээс бага** байх ёстой.

### Reliability — `/pay`

`/pay` endpoint нь ойролцоогоор 5% алдаа зориудаар гаргадаг. 20 VU хэвийн төлбөрийн хүсэлт явуулах үед error rate-ийг хэмжинэ. SLO-г **8%-иас бага** гэж авсан.

### Availability — серверийн тасалдал

2 минутын тестийн үед серверийг түр зогсоож, ойролцоогоор 10 секундын дараа дахин асаасан. 
Сервер асмагц хүсэлтүүд хэвийн үргэлжлэх ёстой. Availability нь **90%-иас дээш** байх ёстой.


### Нэмэлт — `/report`


`/report` endpoint зориудаар 200–400 ms delay-тэй. 20 VU үед p95 latency-г хэмжиж, **450 ms-ээс бага** байх босго тавьсан.

# 3. SLO

| Сценарио | SLI | Босго | Цонх / нөхцөл |
|---|---|---|---|
| Performance — Cart | `/cart/add` p95 latency | **< 20 ms** | 20 VU, 1 минут |
| Reliability — Payment | `/pay` error rate | **< 8%** | 20 VU, 1 минут |
| Availability | Successful checks / нийт checks | **> 90%** | 20 VU, 2 минут, серверийн тасалдалтай |
| Performance — Report | `/report` p95 latency | **< 450 ms** | 20 VU, 1 минут |

### Босго сонгосон үндэслэл

`/cart/add` endpoint localhost дээр маш хурдан ажиллаж байгаа тул 200 ms зэрэг хэт сул босго тавихын оронд p95 < 20 ms гэсэн илүү утгатай босго сонгосон. Бодит PASS туршилтын p95 нь 2.91 ms байсан тул энэ SLO хангалттай margin үлдээж байгаа боловч performance-ийн мэдэгдэхүйц regression-ийг барих боломжтой.

`/pay` endpoint-ийн кодод ойролцоогоор 5% алдаа зориудаар үүсдэг тул санамсаргүй хэлбэлзлийг тодорхой хэмжээгээр зөвшөөрч error rate < 8% гэж сонгосон. PASS туршилтад бодит error rate 5.60% байсан.

Availability-ийн босгыг >90% гэж сонгосон. Ингэснээр 2 минутын туршилтын хугацаанд 10%-ийн error budget зөвшөөрөгдөнө.

`/report` endpoint өөрөө 200–400 ms delay үүсгэдэг тул p95 < 450 ms босго нь тухайн endpoint-ийн зориудын зан төлөв болон бага хэмжээний processing overhead-ийг хамруулсан бодитой босго гэж үзсэн.

# 5. Error budget

Availability SLO:

```text
Availability > 90%
Window = 2 минут = 120 секунд
```

10%-ийн тасалдал зөвшөөрөгдөнө:

```text
120 секунд × 0.10 = 12 секунд
```

Иймээс **time-based error budget = 12 секунд (ойролцоогоор)**. 

Chaos туршилтаар серверийг ойролцоогоор 10 секунд зогсоосон. Цэвэр хугацаагаар авч үзвэл энэ нь 12 секундийн theoretical error budget дотор багтаж байгаа мэт харагдана.

Гэхдээ k6-ийн `checks` нь хугацааны хувь биш, **хүсэлтийн хувь** хэмждэг. Сервер хэвийн ажиллах үед `/report` хүсэлт 200–400 ms хүлээдэг бол сервер унтарсан үед `connection refused` бараг агшин зуур буцдаг. Иймээс downtime-ийн нэг секундэд хэвийн ажиллагааны нэг секундээс илүү олон failed request үүсэх боломжтой бөгөөд time-based болон request-based error budget хооронд ялгаа гарсан.

# 6. Mini chaos туршилт

Chaos туршилтыг 20 VU, 2 минут ажиллуулсан. Туршилтын явцад серверийг гараар зогсоож, ойролцоогоор 10 секундын дараа дахин асаасан.

Chaos-ийн бодит үр дүн:

| Үзүүлэлт | SLO | Бодит үр дүн | Үр дүн |
|---|---:|---:|---|
| Checks / Availability | > 90% | **88.83%** | FAIL |
| `/cart/add` p95 | < 20 ms | **2.66 ms** | PASS |
| `/report` p95 | < 450 ms | **389.76 ms** | PASS |
| `/pay` error rate | < 8% | **13.92%** | FAIL |

Нийт:

```text
Нийт хүсэлт/check = 5667
Амжилттай = 5034
Амжилтгүй = 633
```

Request-based availability:

```text
5034 / 5667 × 100 = 88.83%
```

Иймээс availability SLO болох >90% **хангагдаагүй**.

90%-ийн SLO нь 5667 хүсэлтийн ойролцоогоор 10% буюу:

```text
5667 × 0.10 ≈ 567 хүсэлт
```

хүртэл алдах request-based error budget өгч байна.

Бодитоор:

```text
633 хүсэлт амжилтгүй
```

болсон тул request-based error budget ойролцоогоор 66 хүсэлтээр хэтэрсэн.

Энэ нь дээрх 12 секундийн time-based budget-тэй шууд адил биш. Гар аргаар үүсгэсэн ойролцоогоор 10 секундын тасалдал хугацааны хувьд budget дотор багтаж болох боловч connection refused хүсэлтүүд хурдан буцсан тул request count дээр failure-ийн эзлэх хувь 10%-аас давсан.

Мөн chaos үед `/pay` error rate **13.92%** болсон тул reliability SLO бас FAIL болсон. Үүний шалтгаан нь сервер ажиллаж байх үед зориудын ~5% payment failure гарахаас гадна сервер бүхэлдээ унтарсан үед `/pay` руу чиглэсэн бүх хүсэлт мөн амжилтгүй болсонтой холбоотой.

Availability болон reliability SLI-г production системд илүү зөв тусгаарлахын тулд connection refused зэрэг service-level outage-ийг availability metric-д, харин сервер reachable байх үед гарсан `/pay` HTTP 500 зэрэг payment-specific алдааг reliability metric-д тусдаа custom metric/tag-аар хэмжих нь илүү зөв гэж үзсэн.

Бүтэн chaos гаралт:

```text
results/chaos.txt
```

# 7. Threshold-ийг зориудаар эвдсэн туршилт

FAIL туршилтад `/report` endpoint-ийн threshold-ийг:

```text
p(95) < 450 ms
```

-аас зориудаар:

```text
p(95) < 100 ms
```

болгон өөрчилсөн.

Гэтэл `/report` endpoint өөрөө 200–400 ms delay үүсгэдэг тул энэ шаардлага биелэх боломжгүй.

Бодит үр дүн:

| Үзүүлэлт | Threshold | Бодит үр дүн | Үр дүн |
|---|---:|---:|---|
| Checks | > 90% | 98.20% | PASS |
| `/cart/add` p95 | < 20 ms | 2.55 ms | PASS |
| `/report` p95 | **< 100 ms** | **391.44 ms** | **FAIL** |
| `/pay` error rate | < 8% | 5.39% | PASS |

k6 дараах exit code буцаасан:

```text
exit=99
```

Ингэснээр performance threshold зөрчигдөх үед k6 non-zero exit code буцаадаг болохыг харсан. CI/CD pipeline дээр ийм exit code ашиглан performance SLO зөрчсөн build эсвэл deployment-ийг автоматаар зогсоож болно.

Бүтэн гаралт:

```text
results/fail.txt
```

# 8. Локал тестийн орчны тухай ажиглалт

Энэ лабораторийн тестүүд localhost дээр явагдсан тул гаднын интернет холболтын latency, routing, packet loss болон remote серверийн ачаалал зэрэг хүчин зүйлс үр дүнд бараг нөлөөлөөгүй. Иймээс хэмжилт нь production deployment-ийг шууд дуурайж байгаа гэсэн үг биш боловч application-ийн өөрийн performance болон failure behavior-ийг илүү тусгаарлагдсан орчинд харахад давуу талтай байв.

Өмнөх лабораторид бодит test server рүү load test хийж network болон server behavior хамтад нь хэмжсэн бол энэ лабораторид өөрийн локал API-г зориудаар удаашруулах, failure үүсгэх, бүр серверийг бүхэлд нь унтраах замаар quality scenario-г хяналттай туршиж үзсэн. Ялангуяа гадаад орчноос хамааралгүй локал API дээр ч availability болон reliability failure-ийг бодитоор үүсгэж, k6 threshold автоматаар илрүүлж чадсан нь сонирхолтой байв.

# 9. Дүгнэлт

Энэ лабораторийн хамгийн чухал хэсэг нь ерөнхий шаардлагыг хэмжигдэхүйц scenario, SLO, дараа нь автомат threshold болгон дарааллаар хувиргах байсан. `/cart/add` endpoint-ийн p95 2.91 ms гарсан тул localhost орчинд performance SLO маш тогтвортой хангагдсан. `/pay` endpoint-ийн 5.60% error rate нь кодод зориудаар оруулсан ойролцоогоор 5%-ийн алдаатай ойролцоо байсан бөгөөд 8%-ийн reliability SLO-г хангасан. `/report` endpoint-ийн p95 389.99 ms байсан нь зориудаар оруулсан 200–400 ms delay-тай нийцэж, 450 ms SLO-г хангасан. Chaos туршилтын үед availability 88.83% болж буурсан тул >90% SLO зөрчигдсөн. Мөн `/pay` error rate 13.92% болсон нь нэг серверийн outage availability болон reliability гэсэн хоёр өөр SLO-д зэрэг нөлөөлж болохыг харуулсан. Time-based error budget 12 секунд байсан ч request-based хэмжилтээр 633 хүсэлт амжилтгүй болж budget хэтэрсэн нь хэмжүүрийн төрлийг зөв сонгох шаардлагатайг харуулсан. Зориудаар `/report` threshold-ийг 100 ms болгосон үед p95 391.44 ms гарч FAIL болсон бөгөөд k6 exit code 99 буцаасан. Энэ ажлаар scenario-г зөв тодорхойлж, түүнээс бодитой SLO гаргаад threshold-оор автоматаар шалгах нь CI/CD quality gate-ийн үндсэн зарчим болохыг илүү ойлгосон.

# 10. AI coverage — нэмэлт даалгавар

AI туслахад `server.js`-ийн зан төлөв болон лабораторийн шаардлагыг өгч 6 хэсэгтэй quality scenario болон түүнд тохирох SLO/threshold санал болгуулсан. AI `/cart/add`-д p95 < 20 ms, `/pay`-д error rate < 8%, availability-д >90%, `/report`-д p95 < 450 ms гэсэн босгуудыг санал болгосон бөгөөд бодит PASS туршилтын үр дүнтэй харьцуулахад эдгээр нь тухайн локал системд боломжийн байсан. Гэхдээ AI-аас шууд авсан тоон босгыг хэмжилтгүйгээр зөв гэж үзэх нь буруу бөгөөд ялангуяа localhost дээр 200 ms гэх мэт ерөнхий performance босго хэт сул байж болохыг бодит хэмжилтээр шалгасан. AI нь endpoint-үүдийн өгөгдсөн behavior-оос гадуур шинэ external service эсвэл зохиомол өдөөлт нэмээгүй бөгөөд availability сценариод серверийн crash/restart-ийг үндсэн stimulus болгон хадгалсан. AI-ийн давуу тал нь scenario → SLO → threshold гэсэн холбоог хурдан бүтцэд оруулж, код болон README-ийн босгуудыг ижил байлгахад тусалсан явдал байв. Харин chaos туршилтын time-based болон request-based error budget яагаад зөрж байгааг зөв ойлгохын тулд бодит `chaos.txt` гаралтыг өөрөө шинжилж, AI-ийн саналтай заавал тулгаж шалгах шаардлагатай байсан. Иймээс AI нь эхний бүтэц болон шалгах зүйлсийг гаргахад ашигтай боловч эцсийн SLO-г бодит хэмжилт, системийн behavior болон туршилтын гаралтад үндэслэн баталгаажуулах шаардлагатай гэж дүгнэв.
